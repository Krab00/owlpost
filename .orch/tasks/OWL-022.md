## Description
Finding from the first real cross-machine exchange (2026-09-04, Krzysiek → Krab00 about
`README.md`). `/owlpost:inbox` rendered a one-row table and a list of `owl ...` commands, and
the user had to (a) ask for the question text, (b) learn that the record was in `consent`
state, (c) be told which `owl allow` flag to type. Three defects in `commands/inbox.md` and
`skills/owlpost/SKILL.md`:

1. **Question text is hidden.** `owl inbox` prints rows only; the text lives in `owl show`.
   The command never tells the agent to run `owl show`, so the human sees "README.md, 3m" and
   not "Powiedz mi jak dlugie u Ciebie jest readme?".
2. **`consent` state is unknown to the plugin.** The answer loop in SKILL.md starts at
   `pending`. `owl allow` / `owl deny` appear nowhere in `inbox.md`, its `allowed-tools`, or
   the skill, so the agent can only echo the CLI hint and leave the human to type it.
3. **Choices are offered as command lists, not as a picker.** The agent prints
   "run `owl send <id>` / `owl reject <id>`" instead of using `AskUserQuestion` the way
   `/owlpost:ask` already does. The human ends up typing commands into a chat.

Rewrite `commands/inbox.md` (and the "answer loop" section of SKILL.md) so the flow is:

- Run `owl inbox --json`. Empty → one line, stop.
- For every record in `consent` state: run `owl show <id>`, print the question verbatim in a
  code block with peer name, fingerprint, project and path, then `AskUserQuestion` with
  **Allow once / Allow always / Deny / Skip**. Run `owl allow <fp> --once|--always` or
  `owl deny <fp>` on the pick. `--always` for a hand-added contact needs
  `--i-verified-the-fingerprint`; the option description must say the human confirms the
  fingerprint out-of-band first.
- For `pending` records: single record → `owl show` and print the question at once; several →
  show the table, `AskUserQuestion` to pick one, then `owl show`. Offer **Draft / Reject /
  Skip** via `AskUserQuestion`.
- For `drafted` records: print the draft verbatim in a code block (never paraphrased), then
  `AskUserQuestion` with **Send / Edit / Reject**. `owl send` only on "Send". After `owl edit`
  show the draft again and ask again.
- For `answer` records: print the answer verbatim and apply the SKILL.md memory rule.
- Note in the draft step when the draft's language differs from the question's language
  (Krzysiek asked in Polish, the harness answered in English) and offer `owl edit`.
- `allowed-tools`: `Bash(owl inbox:*)`, `Bash(owl show:*)`, `Bash(owl allow:*)`,
  `Bash(owl deny:*)`, `Bash(owl draft:*)`, `Bash(owl edit:*)`, `Bash(owl send:*)`,
  `Bash(owl reject:*)`. Nothing else.

The ground rule stands: `owl send`, `owl allow --always` and `owl deny` run only after an
explicit human pick; the agent never sends or trusts on its own. `/owlpost:allow` and
`/owlpost:deny` from OWL-021 stay as standalone entry points; this task makes the inbox flow
reach them without leaving the chat.

Out of scope: changes to the `owl` CLI or daemon; changing `owl inbox` output format.
