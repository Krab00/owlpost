## Description
Today the contact book merges two providers, `.agents/peers/*.json` in the git root (`repo`)
and `$OWLPOST_HOME/contacts/*.json` (`local`), but the user cannot tell them apart in the
CLI beyond a `SOURCE` column, cannot list one scope alone, and `owl add` prints
`not implemented yet` — the only way to add a colleague is to copy the JSON by hand into the
home directory (observed 2026-09-05).

Name the scopes the way users think about them: **global** = the user's own book in
`$OWLPOST_HOME/contacts/` (every repo on this machine), **local** = the repository's
`.agents/peers/` (shared with the team via PR). Implement:

- `owl add <peer-file.json> [--local]` — validates the file (name, pubkey, optional emails
  and endpoints), refuses a pubkey already present in either scope, writes it as
  `<slug>.json` into the global book, or into `.agents/peers/` of the current repo with
  `--local`, and prints `added <name> <fingerprint> (global|local)`. TOFU rule from
  `docs/architecture.md` §4 unchanged: adding never sets a policy; `owl allow` does.
- `owl contact list [--global|--local]` — the `SOURCE` column reads `global` / `local`
  (rename of `local` / `repo`; policy overlays still print the scope they live in);
  without a flag both scopes are listed, merged as before.
- `owl contact remove <peer> [--local]` — deletes the file from the named scope (default
  global); refuses to touch `.agents/peers/` without `--local`.
- `/owlpost:me` output tells the colleague to run `owl add <file>` (already does) — no
  change needed once `owl add` exists.

Out of scope: editing contacts in place, fetching a peer file over the network
(`owl card <peer>` already fetches a card), an interactive picker (OWL-020).
