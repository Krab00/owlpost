## Description
Security finding (2026-09-03, protocol review): `tls::spki_pubkey` in `src/tls.rs` does not parse
the certificate; it scans the whole DER for the first occurrence of the 12-byte Ed25519 SPKI
header and takes the 32 bytes after it. In X.509 the serial number, issuer and subject precede the
SubjectPublicKeyInfo, so an attacker who knows a victim's public key (it is public, in
`.agents/peers/`) can embed `<SPKI header><victim pubkey>` in the serial or a DN attribute of a
certificate signed with the attacker's own key. Rustls verifies the handshake signature with the
real key in the certificate (the attacker's), while `PinnedClientVerifier`, `PeerAcceptor` and
`PinnedServerVerifier` take the *victim's* key from the scan. Confirmed by probe on `main`: such a
certificate completed the handshake and was identified as the victim's fingerprint. Consequences:
impersonate any contact (ask in their name, bypass consent/`auto` policy, read and ack their
outbox), and impersonate a responder's server to whoever can redirect traffic.

Fix: extract the SPKI by walking the DER structure (Certificate → TBSCertificate → [0] version →
serialNumber → signature → issuer → validity → subject → SubjectPublicKeyInfo), accept only an
SPKI whose AlgorithmIdentifier is exactly `id-Ed25519` (1.3.101.112, no parameters) and whose
BIT STRING holds 32 bytes with zero unused bits; anything else is rejected. A minimal TLV walker
(~30 lines, no new crate) is preferred; `x509-parser` is acceptable with a one-line justification
per `docs/technical-design.md §1`. Remove the `ponytail:` byte-scan note. Update
`docs/technical-design.md` / `docs/architecture.md §4` only if their wording describes the scan.

Adversarial probes (throwaway tests, removed; worktree clean after):
- (a) pattern in issuer DN (rcgen `signed_by` with issuer CN = pattern, and hand-built): `old_scan == victim`, walker == attacker. Pattern in custom extension (rcgen + hand-built, extension after SPKI): walker == real key, no over-read.
- (b) victim's genuine cert + CertificateVerify signed with attacker's key: server `invalid peer certificate: BadSignature`, no fingerprint served. Walker returns victim on that cert (correct by design; rustls stops this vector). Server-side twin: rustls refuses the cert/key pair at config time (`KeyMismatch`).
- (c) NULL params `05 00` → "must not carry algorithm parameters"; empty SEQUENCE params also rejected.
- (d) 33-byte key, unused 0 → "got 33"; also 64 and 0 rejected.
- (e) `[0]` present with value v1 (0): **accepted** (walker skips the version value). Not required by AC; harmless — SPKI position is unchanged and rustls/webpki still parse the cert.
- (f) zero-padded serial (hand-built `02 03 00 80 01`, and rcgen MSB-set serial which rcgen zero-pads): accepted, correct key.
- (g) non-minimal long-form lengths (`0x82 00 xx`, `0x83 00 00 xx`, `0x84 00 00 00 xx`, inner `0x81 01`): **accepted by the walker**. Decision: not required. On the wire, rustls (webpki inside `verify_tls13_signature`) rejects such a certificate with `invalid peer certificate: BadEncoding` before our verifier's key matters (probe with a custom `ResolvesClientCert`; trailing garbage also `BadEncoding`; control genuine cert Ok). So the walker can never be reached with a cert webpki would parse differently.
- (h) every cert-parsing path goes through `spki_pubkey`: `PinnedClientVerifier` (tls.rs:180), `PinnedServerVerifier` (tls.rs:233), `PeerAcceptor` via `peer_fingerprint_from_cert` (server.rs:634). No other `windows(`/scan in `src/`.
- Extra: length corners (`0x84 ff ff ff ff` → truncated, `0xff` → unsupported, `30 81` → truncated length), every `expect` step with a wrong tag (B1, B4–B12) each yields its own error, OID prefix/suffix/Ed448/empty all rejected, unused bits 7/255 rejected, every-prefix truncation of the long-form fixture, `0x81` outer length walked, TOFU server verifier on forged cert accepts but identifies the **attacker** (so `owl add` records the attacker, never the victim), walk error → `rejected()` in both verifiers, unpinned-card mode still rejects forged client (G2), TOFU client on forged server sees attacker fingerprint (G4), invalid Ed25519 point reaches "invalid ed25519 key" (C12), trailing bytes after Certificate ignored by walker.
