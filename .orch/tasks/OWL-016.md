## Description
Security finding (2026-09-03, protocol review): `tls::spki_pubkey` in `src/tls.rs` does not parse
the certificate; it scans the whole DER for the first occurrence of the 12-byte Ed25519 SPKI
header and takes the 32 bytes after it. In X.509 the serial number, issuer and subject precede the
SubjectPublicKeyInfo, so an attacker who knows a victim's public key (it is public, in
`.agents/peers/`) can embed `<SPKI header><victim pubkey>` in the serial or a DN attribute of a
certificate signed with the attacker's own key. Rustls verifies the handshake signature with the
real key in the certificate (the attacker's), while `PinnedClientVerifier`, `PeerAcceptor` and
`PinnedServerVerifier` take the *victim's* key from the scan. Confirmed by probe on `main`: such a
certificate completed the handshake and was identified as the victim's fingerprint. Consequences:
impersonate any contact (ask in their name, bypass consent/`auto` policy, read and ack their
outbox), and impersonate a responder's server to whoever can redirect traffic.

Fix: extract the SPKI by walking the DER structure (Certificate → TBSCertificate → [0] version →
serialNumber → signature → issuer → validity → subject → SubjectPublicKeyInfo), accept only an
SPKI whose AlgorithmIdentifier is exactly `id-Ed25519` (1.3.101.112, no parameters) and whose
BIT STRING holds 32 bytes with zero unused bits; anything else is rejected. A minimal TLV walker
(~30 lines, no new crate) is preferred; `x509-parser` is acceptable with a one-line justification
per `docs/technical-design.md §1`. Remove the `ponytail:` byte-scan note. Update
`docs/technical-design.md` / `docs/architecture.md §4` only if their wording describes the scan.

## Acceptance criteria
- [ ] AC1: unit test `tls::tests::spki_from_der_walk` asserts `spki_pubkey` on a certificate built by `cert_from_identity` returns exactly the identity's 32-byte verifying key, and `peer_fingerprint_from_cert` returns its fingerprint (modality: test)
- [ ] AC2: unit test `tls::tests::embedded_victim_key_in_serial_is_rejected` builds, with rcgen and the attacker's key, a certificate whose serial number is `<SPKI Ed25519 header><victim pubkey>` and asserts `spki_pubkey` returns the attacker's key, never the victim's; a twin test places the pattern in a subject DN attribute (CommonName) and asserts the same (modality: test)
- [ ] AC3: integration test `tests/tls.rs::forged_spki_certificate_fails_handshake` — daemon lists only the victim as a contact; a client presenting an attacker-signed certificate with the victim's key pattern embedded (serial and CN variants) fails the TLS handshake against `server_config` (pinned mode), and the daemon never records or serves anything for that connection; the genuine victim certificate still connects (modality: test)
- [ ] AC4: unit test `tls::tests::pinned_server_verifier_rejects_forged_spki` asserts `client_config` pinned to the victim's key rejects a server presenting the forged certificate, and accepts the genuine one (modality: test)
- [ ] AC5: negative-shape tests for the DER walker: SPKI with a non-Ed25519 OID (X25519 1.3.101.110), SPKI with parameters present, BIT STRING with a non-zero unused-bits byte, key length 31 and 33, truncated certificate, and a certificate whose TBSCertificate omits the `[0] version` field — each returns `Err`, never panics (modality: test)
- [ ] AC6: the byte-pattern scan and its `ponytail:` note are gone from `src/tls.rs` (`grep -n "windows(SPKI_ED25519_HEADER" src/tls.rs` finds nothing) and the existing `tests/tls.rs` suite still passes unchanged (modality: data)
