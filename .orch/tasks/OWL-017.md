## Description
Finding from the first cross-machine test (2026-09-04): the only endpoint owlpost can advertise
today is a host:port that the *asker* must be able to dial (`docs/concept.md` "Addressing — hard
prerequisite"). Two people on different networks — home LAN and a corporate laptop, or Poland and
the US — have no such address unless both run a VPN or Tailscale, and the concept's open question
"which stable-DNS option exists in the company" has no answer yet. Without this, the pilot cannot
start with anyone outside one office network.

Add a second transport to the daemon and to `owl ask` / the pull loop, built on the `iroh` crate
(Rust, open source, QUIC): a peer is dialed **by its ed25519 public key**, iroh finds a direct
path by hole punching and falls back to a public relay when it cannot. Nothing new to install,
no account, no port forwarding. The fit with the existing design is deliberate:

- iroh's endpoint identity is an ed25519 key. The daemon derives its iroh `SecretKey` from the
  same 32-byte seed as `identity::Identity` (`Identity::seed()` → `iroh::SecretKey::from_bytes`),
  so the iroh endpoint id **is** the contact's `pubkey`. A contact needs no `endpoints` field to
  be reachable; the fingerprint in `.agents/peers/` is the address.
- Peer authentication stays key-pinned: an incoming iroh connection exposes the remote's public
  key; the daemon accepts only keys present in the merged contact book (the same check
  `PeerAcceptor` does for mTLS today). Unknown keys are refused at the connection, never stored.
- The HTTP contract (`docs/technical-design.md` §6) is unchanged: the same `POST /v1/questions`,
  `GET /v1/outbox`, ack, signature header and replay rules are served over an iroh bidirectional
  stream (hyper over the QUIC stream, ALPN `owl/1`). One request handler, two listeners.
- Only the *responder* must be reachable; the asker initiates both the question and the pull.
  That holds for both transports.

`owl ask` and the pull loop try transports in order: **iroh first** (always available once both
sides run this version), then the configured `endpoints` (LAN / VPN, still useful and faster
when they resolve). A contact with an empty `endpoints` list is therefore valid from now on;
`owl doctor` reports the iroh endpoint state (bound, relay connected, id) instead of warning
about missing endpoints.

Design decisions to record in `docs/concept.md` (Addressing) and `docs/architecture.md` (§1, §4
trust table): "no central server" becomes "no server that sees content": the relay carries only
end-to-end encrypted QUIC and learns which two keys talked and when. The default relay set is
n0's public relays (`presets::N0`); `config.json` gains `relay_urls: []` for a self-hosted
relay (iroh's relay server is open source) so a company can keep even the metadata in-house.
The `endpoints`-only path stays for users who refuse any relay; document the trade-off, do not
hide it. `deps` include OWL-016 because the key-pinning check moves to a second code path and
must reuse the audited SPKI-free comparison (iroh hands us the key directly; there is no
certificate to parse).

Out of scope: replacing mTLS on the host:port path, an owlpost-owned relay protocol, QR/invite
bundles (M4). Exact iroh API names (`Endpoint::builder`, `presets::N0`, `alpns`, `connect`,
`remote_id`) are to be verified against the pinned crate version's docs by the implementer;
justify the new crate per `docs/technical-design.md` §1.

## Acceptance criteria
- [ ] AC1: `owl whoami` and `owl contact export` are unchanged in shape; the daemon's iroh endpoint id, printed by `owl doctor`, equals the identity's `pubkey` byte-for-byte — unit test `daemon::tests::iroh_endpoint_id_is_identity_pubkey` (modality: test)
- [ ] AC2: integration test `tests/iroh.rs::question_and_answer_over_iroh` — two daemons in temp homes, contact books pointing at each other **with empty `endpoints`**, both bound to a local iroh relay started in the test (no internet); `owl ask` returns `accepted <id>`, `owl allow` + `owl draft --harness fake` + `owl send` on the responder, and the asker's pull loop stores the answer in `inbox/`, acks it, and the responder moves it to `done/` (modality: test)
- [ ] AC3: integration test `tests/iroh.rs::unknown_key_is_refused` — a third identity not in the responder's contact book connects over iroh; the connection is rejected before any request is read, all five spool dirs stay empty, `seen-ids.txt` is untouched, and the contact book is not modified (no TOFU on the iroh path) (modality: test)
- [ ] AC4: integration test `tests/iroh.rs::signature_and_replay_rules_apply_over_iroh` — over iroh, a body whose `X-Owl-Signature` does not verify gets the same status as over HTTPS, a replayed `id` gets the same status, and the per-peer rate limit triggers `429` at the same threshold; the three responses are asserted equal to the HTTPS suite's expectations from `tests/server.rs` (modality: test)
- [ ] AC5: transport order — integration test `tests/iroh.rs::iroh_first_then_endpoints`: with a contact whose `endpoints` holds one unreachable address and iroh available, `owl ask` succeeds without ever dialing the address (asserted by a listener on that address that records connection attempts); with iroh unavailable (relay map empty, both daemons on isolated sockets) and a reachable endpoint, `owl ask` succeeds over HTTPS; with both unavailable, `owl ask` reports offline in the same wording as today (modality: test)
- [ ] AC6: `config.json` accepts `relay_urls` (list of URLs); `owl doctor` prints `ok iroh: <id short>, relay <url>` when connected, `warn iroh: bound, no relay` when not, and no longer warns about empty `endpoints` — unit test `cli::doctor::tests::iroh_line` covers both lines (modality: test)
- [ ] AC7: `docs/concept.md` "Addressing" and "Open questions", `docs/architecture.md` §1 diagram, §4 trust table and §5 delivery table, and `docs/technical-design.md` (config field, doctor line, crate justification) describe the iroh transport, the relay's metadata visibility and the self-hosted relay option; `tests/docs.rs` still passes (modality: data)
- [ ] AC8: `scripts/e2e-real.sh` gains `OWL_TRANSPORT=iroh|https` (default `https`, unchanged behaviour) and the iroh run completes the same loop against the real harness on one machine using n0's public relays; the run is recorded once by hand in the task file with the relay URL doctor reported (modality: manual, PM-REVIEW)
- [ ] AC9: `cargo build`, `cargo test --workspace`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check` all pass; binary size growth is reported in the PR (iroh pulls QUIC + relay client) (modality: data)
