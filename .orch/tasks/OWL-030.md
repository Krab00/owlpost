## Description
Found by OWL-029 AC8 on the dev machine (2026-09-06 19:15 UTC): the first real `owl update --source .`
with the OWL-029 binary printed `installed /home/kris/.local/bin/owl` and then rewrote the systemd
unit as `ExecStart="/home/kris/.local/bin/owl (deleted)"`; the daemon went into a 203/EXEC restart
loop (12 restarts) until the unit was repaired by hand. `owl doctor` showed
`warn binary: daemon unit runs /home/kris/.local/bin/owl (deleted)` and `fail daemon: … Connection refused`.

Root cause: `run_update` (`src/cli/update.rs`) computes `active = install::owl_path()` once, replaces
the file by rename, and then calls `install::uninstall()` + `install::install(home, false)`;
`install::install` (`src/cli/install.rs:229`) calls `owl_path()` **again**. After the rename the
running process's `/proc/self/exe` reads `<path> (deleted)`, `canonicalize` fails (the path no
longer exists as an inode) and the raw string is written into the unit. The OWL-029 end-to-end
tests never hit this because `OWLPOST_UPDATE_ACTIVE` redirects the replaced file away from the
running test binary.

Fix, smallest that closes it:
- `install::install` takes the owl path from its caller: `pub fn install(home, dry_run, owl: &Path)`
  (or an `install_with(owl)` used by update; the CLI `owl install` keeps resolving `owl_path()`
  itself). `run_update` passes the `active` it computed **before** the replacement, so the unit
  is written from a value read while the file still existed.
- Defence in depth: `install::owl_path()` strips a trailing ` (deleted)` from `current_exe()`
  before canonicalising (Linux `/proc/self/exe` artefact), with a `// ponytail:` naming the
  artefact, so `owl doctor`, `owl install` and anything else that resolves the running binary
  after an in-place replacement report the real path.
- The doctor `binary` check reuses `owl_path()` (it already does) and therefore stops printing
  `(deleted)`.
- Design doc §11: one sentence — the unit is rewritten from the path captured before the
  replacement; a running process's own path may read `(deleted)` after a rename on Linux.
- README/quickstart: one line for installs older than OWL-029: the first `owl update` still runs
  the old updater (installs to `~/.cargo/bin`); bootstrap once with the two-command copy+rename
  into `~/.local/bin` (or re-run the release installer), then `owl update` works in place.

Out of scope: macOS launchd equivalent (no `(deleted)` artefact there; the caller-passed path fixes
it anyway); the release installer.
