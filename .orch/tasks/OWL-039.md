## Description

Decision (2026-09-14): a thread with a person carries three kinds of request. OWL-034 built the
first (a question). This task adds the second: a peer asks me for a **concrete file** from a
named project at a named ref of my checkout, or for one **entry of a memory store I own**, and
the reply carries the content itself — not a ≤ 8 KiB snippet, real content transfer.

Three rules hold without exception and are the point of the task:

1. **Manual consent, per request, every time.** A content request from a peer whose policy is
   `auto` is held for consent exactly like one from a peer with no policy. Policy `never` still
   short-circuits to `403` at the API. There is no mode in which content leaves the machine
   without a human running `owl send` (or pressing the mod's **Send**, which runs `owl send`).
2. **The allowlist is explicit.** Only a path inside a checkout named in `config.projects`, or
   inside the configured `memory_root`, can be served. Anything else is refused with a `4xx` at
   the API and never reaches consent, never reaches the spool, never wakes a session.
3. **Nothing runs at arrival.** The daemon stays a mailbox: it validates the request and spools
   it. The file is read only when the human runs `owl draft <id>`, and the redaction regexes of
   §10 run over the content exactly as over a drafted answer.

### 1. Envelope (§6) — two new `Kind` variants, not a body discriminator

`Body` is `#[serde(untagged)]`: serde takes the first variant whose fields fit, so a
discriminator inside the body would let a missing field silently select the wrong variant. Two
new `Kind` variants give an explicit tag and turn every `match` on `Kind`/`Body` into a compile
error the implementer must answer — the safer failure mode.

```rust
pub enum Kind {
    Question, Answer,
    #[serde(rename = "content")]      Content,
    #[serde(rename = "content-reply")] ContentReply,
}
```

`Kind` carries `#[serde(rename_all = "lowercase")]`, so `ContentReply` would go out as
`contentreply` without the explicit rename; the wire names are `content` and `content-reply`.

New `Body` variants, appended after `Question` and `Answer` (order matters for an untagged
enum; each is disjoint from the existing two because `Question` requires `question` and
`Answer` requires `answer`):

```json
{ "project": "github.com/company/monorepo", "ref": "main", "path": "src/auth/session.rs" }
{ "memory": "decisions/2026-08-refresh-token.md" }
```

```rust
Content {
    #[serde(default, skip_serializing_if = "Option::is_none")] project: Option<String>,
    #[serde(rename = "ref", default, skip_serializing_if = "Option::is_none")] git_ref: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")] path: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")] memory: Option<String>,
},
ContentReply {
    content: String,
    sha256: String,
    #[serde(default, skip_serializing_if = "Option::is_none")] ref_resolved: Option<String>,
    truncated: bool,
    redactions: u32,
    harness: String,      // always "human"
},
```

- `ref` is a Rust keyword, hence the field name `git_ref` with the `serde(rename)` that keeps
  the wire key. Default when the asker sends none: the checkout's current branch, resolved and
  reported back in `ref_resolved` (the commit hash, 40 hex chars).
- Exactly one of `path` (with `project`) and `memory` is present; both or neither is a `400`.
- `context_id` behaves exactly as for a question: `owl request` mints one, `--reply-to <id>`
  copies an existing thread's, the reply copies the request's (`Payload::content_reply` mirrors
  `Payload::answer`, `src/envelope.rs:93`).
- `MAX_CONTENT_BYTES: usize = 262_144` (256 KiB) — the content after redaction. Beyond it the
  content is cut at the last complete UTF-8 character and `truncated: true` goes out; the reply
  always carries the `sha256` of the **full** content before the cut, so the asker can tell it
  received a prefix. A file that is not valid UTF-8, or that contains a `NUL` byte, is refused —
  this task transfers text, never binaries.
- `envelope::a2a_state` needs **no new row**: it keys on the spool state string, which the new
  kind shares with a question.

### 2. Config (§3) — `memory_root`

```json
"responder": { …, "memory_root": "/Users/krzysiek/notes/owlpost" }
```

`Option<String>`, absent by default (`owl init` writes nothing for it), canonicalised on load.
With no `memory_root` every `memory` request is refused `400 memory store not configured`.
`responder.scope.private_memory` (already in §3, default `false`) must also be `true`, so the
existing switch keeps its meaning: `memory_root` says *where*, `private_memory` says *whether*.

### 3. Server (§7) — the same route, one refactor point

`POST /v1/questions` accepts the new kind; no new route. A second route would need its own
mTLS wiring, its own iroh mount, its own forward-route row and its own rate-limit story, and
`GET /v1/questions/{id}` already answers the A2A `Task` for any record by id — the asker's view
of a content request is the same view. The route's name stays `questions` (renaming it would
break every pinned test and every deployed peer).

`src/server.rs:456 validate_question` becomes `validate_request(value, caller, me)`, dispatching
on `type`: `question` keeps **every** existing check and error string byte-identical (the tests
pin them), `content` adds:

| Check | Response |
|---|---|
| `type` not one of `question`, `content` | `400 type must be question or content` |
| both or neither of `body.path` and `body.memory` | `400 body must carry exactly one of path and memory` |
| `body.path` without `body.project` | `400 missing body.project` |
| `body.project` not a key of `config.projects` | `400 unknown project` |
| `body.path` absolute, empty, or containing a `..` segment (after `\` → `/`) | `400 path escapes the project` |
| `body.memory` absolute, empty, or containing a `..` segment | `400 memory key escapes the memory store` |
| `body.memory` with no `responder.memory_root` or `scope.private_memory == false` | `400 memory store not configured` |
| `body.ref` longer than 200 bytes or carrying a byte outside `[A-Za-z0-9._/-]` | `400 malformed ref` |

The daemon does **not** stat or read the file here: a `path` inside the allowlist that does not
exist reaches consent and fails at `owl draft` (`unknown path <p> at <ref>`, exit 1). Reading
the disk at arrival would let an unanswered peer probe for file existence by timing, which the
consent gate exists to prevent.

After validation:

- policy `never` or responder disabled → `403 {"error":"unavailable","state":"TASK_STATE_REJECTED"}`,
  unchanged;
- otherwise the record is spooled in state **`consent`** whatever the policy is. `server::record_state`
  gains the kind: `record_state_for(kind, mode)` returns `("consent", false)` for `Kind::Content`
  for every mode, and delegates to today's table for `Kind::Question`. The `auto` flag it returns
  is `false`, so the scheduler is never even offered the record;
- the caches are skipped in both directions: no `cache_get`, no `cache_put` (`may_read_cache` is
  not consulted for the new kind, and `answer::send` writes no cache entry for it). Content is
  keyed by ref and by consent, not by question text;
- `202 {"status":"accepted","id":"…","state":"TASK_STATE_SUBMITTED"}` — always SUBMITTED,
  because the record is always held.

`src/auto.rs::not_a_candidate` gains an explicit first guard: a record whose payload kind is not
`Kind::Question` is `Skipped("record <id> is a content request — consent only")`. Today the
scheduler would fall through `answer::question_body(…).is_err()`; an explicit guard is what a
test can pin, and what a later kind inherits.

### 4. CLI (§9)

- **Asker** — `owl request <peer> <project> <path> [--ref <ref>] [--reply-to <id>]` and
  `owl request <peer> --memory <key> [--reply-to <id>]`. Sends the payload, stores an `asks/`
  record (event `content-requested`), prints `accepted <id> — waiting for the owner's consent`
  (`--json` adds `"state"`), exit 2 offline, exit 3 rate limited, as `owl ask`. `--wait` is not
  offered: a human reads a file and approves it, so the wait is human-scale and `owl status`
  already reports it.
- **Responder** — the record flows through the existing verbs unchanged: `owl inbox` lists it
  with `type: "content"` and `summary` = `<path>@<ref>` (or `memory:<key>`), `owl allow` /
  `owl deny` handle consent exactly as for a question, `owl show` prints the request, and:
  - `owl draft <id>` on a content record takes **no harness and no model**. It resolves the ref
    in the project's checkout (`git rev-parse <ref>^{commit}`, then `git show <commit>:<path>`;
    for `memory` it reads `<memory_root>/<key>` and `ref_resolved` is absent), refuses a
    non-UTF-8 or `NUL`-carrying file (`exit 1 <path> is not text`), runs
    `runner::redact(&config.responder.redact, &content)`, cuts at `MAX_CONTENT_BYTES`, stores the
    result as the draft (`harness: "human"`, `redactions`, `truncated`, `sha256`, `ref_resolved`)
    and prints
    `content: src/auth/session.rs@a1b2c3d (4821 bytes, 2 redactions)`
    (`truncated, 262144 of 981233 bytes` appended when cut). `--harness`, `--text`, `--agent` and
    `--prompt` on a content record are a usage error (`exit 1 record <id> is a content request — run owl draft <id> with no flags`).
  - `owl show <id>` prints the request (project, ref, path or memory key) and, once drafted, the
    content in a plain ```` ```text ```` block under `content:` — up to a display cap of 200 lines,
    beyond which it prints the first 200 lines plus `… <n> more lines — <bytes> bytes, sha256 <hex>`.
    `--format claude` renders the peer's request as the message table and our content as that
    block, never as a table.
  - `owl send <id>` signs a `content-reply` payload and queues it in `outbox/` exactly as for an
    answer (`answer::send` branches on the kind for the payload it builds, everything else —
    `existing_answer`, `log/outgoing.jsonl`, `finish`, the event) is shared. `send` must also skip
    the question hash for the new kind: `answer::question_body` errors on a `Content` body, so the
    `envelope::question_hash` call and the `meta.hash` key of the outbox record are omitted, not
    only the cache write.
  - `owl reject <id>` discards it; the peer sees `TASK_STATE_REJECTED`.
- **Asker again** — the pulled reply lands in `inbox/` as a `content-reply` record;
  `owl inbox` shows it, `owl show <id>` prints the content with the same display cap and one
  line `sha256 <hex> — verified` / `sha256 mismatch — the content does not match its digest`
  (exit 1 on a mismatch). Nothing is written to the asker's working tree: the content is in the
  record, and copying it into a file is the human's business.
- **Thread** — `owl thread` gains the event kinds `content-requested` (out, on the `asks/`
  record), `content-drafted` (`by: "human"`, `detail: {bytes, redactions, truncated}`),
  `content-sent` and `content-received`. They are plain strings in `meta.events`, so OWL-038's
  renderer needs no change beyond naming them in its human-format label table.

## Acceptance criteria

One deviation from the brief, decided in §3 and repeated here so it is not missed: **binary and
oversize are not `4xx` at the API**. The daemon does not read the file at arrival (reading it
would let an unanswered peer probe for file existence and size by timing, which the consent gate
exists to prevent), so a non-text or over-cap file is refused by `owl draft` — AC6 — while the
API's `4xx` covers traversal, the allowlist and the request shape — AC2.

- [ ] AC1: a `content` payload round-trips through `Payload`/`Body` with the wire keys `type: "content"`, `ref`, `path`, `memory`, and a `content-reply` with `type: "content-reply"`, `content`, `sha256`, `ref_resolved`, `truncated`, `redactions`, `harness`; a `question` and an `answer` payload byte-identical to today's still parse into `Body::Question`/`Body::Answer` (the untagged order did not shift), and `Payload::content_reply` copies the request's `context_id` (modality: test)
- [ ] AC2: `POST /v1/questions` answers `400` with the exact message for each row of the validation table — both of `path` and `memory`, neither, `path` without `project`, an unknown project, `../../etc/passwd`, an absolute path, a `..` inside a `memory` key, a `memory` request with no `memory_root`, a `memory` request with `private_memory: false`, a malformed `ref` — and in every case `spool/inbox/` stays empty and no session is woken; a valid request answers `202` with `state: "TASK_STATE_SUBMITTED"` (modality: test)
- [ ] AC3: a content request from a peer whose policy is `auto` lands in `inbox/` in state `consent` (not `pending`), `record_state_for(Kind::Content, Some(Mode::Auto))` returns `("consent", false)`, the auto scheduler skips the record with `record <id> is a content request — consent only` after `owl allow --always`, and a `never` peer still gets `403 {"error":"unavailable","state":"TASK_STATE_REJECTED"}`; the positive twin (a *question* from the same auto peer) is still `pending` and still auto-answered (modality: test)

### Open questions for the operator
1. The reply carries the content once and it then lives in the asker's spool for good (`done/` is never pruned by content). Should a content reply expire from the asker's spool on a timer, the way an unacked outbox entry does?
2. `ref` accepts any revision `git rev-parse` resolves, including a commit on a branch that was never pushed. Is that intended, or should the allowlist also name the refs a peer may ask for?
