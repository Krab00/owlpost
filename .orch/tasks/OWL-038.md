## Description

Decision (2026-09-14): the inbox stops being a flat list of records and becomes a **per-person
thread view**. Opening a person shows the whole conversation with them, in both directions and
in one chronological order: what they asked me, what I asked them, what each of us answered,
and what happened to every request on my side — held for consent, allowed or denied, drafted by
which harness or by the human, edited, sent, rejected. Today only one kind of request exists
(a question, OWL-034); OWL-039 (content request) and OWL-040 (tool-call request) each add a
kind to the same timeline. This task builds the timeline and its storage so those two are
additive: the event `kind` is an **open string**, never an enum the renderer matches
exhaustively.

Nothing here changes the wire: no new payload field, no new route, no new state. The daemon
keeps its behaviour; the spool gains a log of what already happened.

### 1. The event log — `meta.events` on the record (`src/events.rs`, new)

**Where**: an array under the record's existing `meta` object, not a sidecar file.
`Spool::move_to` (`src/spool.rs:168`) is a bare `rename` of `<id>.json`, so a sidecar would need
its own atomic move at every `move_to`/`finish` caller and would inherit the blocked-destination
failure-path matrix of OWL-003/010/011 at each of them; `meta` already travels with the record
for free and already carries `peer`, `hash`, `answer_id`, `done_at`, `auto_error`.

```json
"meta": { "peer": "owl:…", "hash": "…", "events": [
  { "ts": "2026-09-14T10:00:00Z", "kind": "received" },
  { "ts": "2026-09-14T10:00:00Z", "kind": "held" },
  { "ts": "2026-09-14T10:04:11Z", "kind": "allowed", "by": "human", "detail": { "scope": "once" } },
  { "ts": "2026-09-14T10:04:40Z", "kind": "drafted", "by": "claude", "detail": { "redactions": 1 } },
  { "ts": "2026-09-14T10:05:02Z", "kind": "sent", "by": "human", "detail": { "answer_id": "0191…" } }
] }
```

- `src/events.rs`: `pub struct Event { ts: String, kind: String, by: Option<String>, detail:
  Option<Value> }` (`skip_serializing_if = "Option::is_none"` on both optionals, so an event
  without them is two keys), `pub fn push(rec: &mut Record, kind: &str, by: Option<&str>, detail:
  Option<Value>)` (stamps `envelope::rfc3339_now()`, appends through `answer::meta_object`, so a
  non-object `meta` is repaired exactly as today), `pub fn of(id: &str, rec: &Record) -> Vec<Event>`
  (the stored log, or the derived one below when `meta.events` is absent, empty or not an array).
- `EVENTS_MAX: usize = 200`. `push` drops the oldest event beyond the cap, never the first
  (`received` / `asked` anchors the timeline). A `state-seen` event is appended only when its
  `detail.state` differs from the previous `state-seen` of the same record, so a tight
  `owl status --wait` poll cannot fill the log.
- **Write points** — two shared helpers plus the three places a record is born, and nowhere else:
  - `Spool::set_state_with_event(dir, id, state, kind, by, detail)` — one `get` + `push` +
    `put`, used by `src/cli/allow.rs:59` (`allowed`, `by: "human"`, `detail: {"scope":
    "once"|"always"}`), `src/pull.rs:258` (`answer-received`) and `src/pull.rs:413` (`expired`).
    `Spool::set_state` stays for callers with nothing to log (`src/server.rs:740` ack).
  - `answer::finish(spool, id, rec, state, extra, event)` gains the event as a parameter (it is
    the single place a record reaches `done/`): `sent` from `answer::send`, `rejected` from
    `src/cli/reject.rs:14`, `denied` from `src/cli/deny.rs:21`, `declined` from `src/pull.rs:279`.
  - Record birth: `src/server.rs::post_question` pushes `received` and then `held` (state
    `consent`) or nothing (state `pending`); `src/pull.rs` pushes `answer-received` on a pulled
    answer; `src/cli/ask.rs` pushes `asked` on the new `asks/` record.
  - `drafted` (`by`: the harness name, or `human` for `owl draft --text`, `agent` for
    `--text --agent`; `detail: {"redactions": <n>, "status": "ok"|"timeout"|"extract_failed"}`)
    is pushed in `answer::draft_*` where `AUTO_ERROR` is already removed
    (`src/answer.rs:276`, `:334`); `edited` (`by: "human"`) in `src/cli/edit.rs`.
  - `state-seen` (`by: "peer"`, `detail: {"state": "TASK_STATE_WORKING", "text": "the owner is
    reviewing the answer"}`) is pushed on an `asks/` record by `owl status` and by
    `owl ask --wait` whenever the peer's Task text changes, and by the daemon's `pull_once`.
- **Legacy records** (nothing writes to them, `of()` derives on read — a read-only command must
  never migrate on read): one event at `rec.received_at`, `received` in `inbox/`/`outbox/`/`done/`
  and `asked` in `asks/`; plus, when `meta.done_at` is present, one event at that timestamp whose
  kind comes from `rec.state`: `answered` → `sent`, `rejected` → `rejected`, `denied` → `denied`,
  `declined` → `denied` (`detail: {"by": "peer"}`), `acked`/`expired` → `sent`, `answered` on an
  `asks/` record → `answer-received`, anything else → no second event. A record that has a stored
  log is never mixed with a derived one.

### 2. `owl thread` — `src/cli/thread.rs` (new), §9 row

**`owl thread [--json]` — the peer list.** One row per peer fingerprint seen in `inbox/`,
`outbox/`, `asks/` or `done/`:

```json
[ { "from": "owl:k7q2m3xz9pdw4hrt", "from_name": "Ania Kowalska",
    "last_ts": "2026-09-14T10:05:02Z", "unseen": 2, "open": 1,
    "last_summary": "Why is the refresh token rotated on every read?" } ]
```

`unseen` = inbox records of that peer with `seen == false`; `open` = inbox questions in state
`consent`, `pending` or `drafted`; `last_summary` = `cli::first_line(text, SUMMARY_CHARS)` of the
newest record. Sorted by `last_ts` descending, `from_name` ascending as the tiebreak (OWL-007:
the fixture must order differently under the two keys). Human format is the `owl inbox` table
renderer with the columns `PEER  UNSEEN  OPEN  LAST  SUMMARY`; nothing to show → exit 4
`no threads`.

**`owl thread <fingerprint|name> [--json] [--since <age|date>] [--context <context_id>]` — the
timeline.** The peer is resolved with `ContactBook::resolve` (§5, all four forms). Every record
of that peer in `inbox/`, `outbox/`, `asks/` and `done/` contributes its events; each event
becomes one row:

```json
{ "ts": "2026-09-14T10:04:40Z", "kind": "drafted", "dir": "in", "record_id": "0191…",
  "context_id": "0191…", "type": "question", "state": "drafted",
  "project": "github.com/company/monorepo", "path": "src/auth/session.rs",
  "text": "<the full question or answer text>", "context": "<body.context, when present>",
  "harness": "claude", "by": "human", "detail": { "redactions": 1 } }
```

- `dir` is `in` for a record the peer sent us (`inbox/`, `done/` questions, pulled answers) and
  `out` for one we produced or sent (`asks/`, `outbox/`, our answers). `text` is the **full**
  question or answer text, never cut — the mod truncates for the eye. `context`, `harness`,
  `by` and `detail` are omitted when absent. `kind` is an open string: an unknown value passes
  through `--json` untouched and renders as its own name in the human format.
- Sorted by `ts` ascending, `record_id` then the event's index in its record as tiebreaks, so
  two events stamped in the same second keep their real order.
- `--since` takes the same argument `owl history --since` takes and drops earlier events;
  `--context <id>` keeps only events of records whose payload `context_id` matches. Both filters
  may be combined; an empty result is exit 0 with an empty array (`[]`) or the header line alone.
- Human format: one header line
  `owl:k7q2m3xz9pdw4hrt — Ania Kowalska · 7 events · last 12:04`, then one block per event,
  blocks separated by one blank line:
  - an event that carries a **peer** message (`kind` `received` or `answer-received`, `dir` `in`)
    prints the `--format claude` message table of that record through `src/render.rs`
    byte-for-byte, so the §9 rule "a table always means from a peer" holds;
  - everything else — our own drafts, our sent answers, our asks, and every bookkeeping event —
    prints one line `HH:MM <kind>[ · by <by>][ · <detail k=v, …>]` and, when the event carries
    our own text (`drafted`, `sent`, `asked`), that text in a plain ```` ```text ```` block, the
    shape `owl show --format claude` already uses for a draft.
- `owl thread` is **read-only**: it never opens a socket, never runs a harness, never marks a
  record seen, never writes into the spool (no routing release, no `seen = true`, no migration
  of a legacy log).

### 3. `context_id` in the existing listings

`owl inbox --json` and `owl history --json` gain one key each, `"context_id"` (the payload's
thread id, `null` when absent), appended to `cli::summary` and to the `history` row after
`path`. Additive: no key is renamed or removed, the human tables are unchanged.

### 4. The mod — `plugins/claude-code/hooks/owlpost.tsx`

The Inbox view becomes two views, both fed by `owl … --json` through the existing `json()`
helper; Contacts and Ask are untouched, and the band above the prompt is untouched.

- `threads` (what the band's **Inbox** button and the Inbox tab now open): rows from
  `owl thread --json`, one `Box` per peer with `Text` `<name> · <unseen> unseen · <open> open`,
  a dim second line with the fingerprint and `last_summary`, and a `Button` **Open** that sets
  `openPeer = row.from` and switches to `thread`.
- `thread`: rows from `owl thread <fingerprint> --json` drawn oldest first, each event one
  `Box` — time, kind, and the text cut to three lines with `<Text wrap="truncate">`. The action
  buttons sit **next to the open request only** (the newest event of a record whose `state` is
  `consent`, `pending` or `drafted`), never on every row: **Allow once** / **Allow always** /
  **Deny** on `consent` (each label carrying the fingerprint, OWL-036), and **Draft (Claude)**
  (`$.command.run({ command: 'owlpost:draft', args: id })`) / an `Input` for the human's own
  answer (`owl draft <id> --text`) / **Send** / **Reject** on an open question. A **Back**
  button returns to `threads`.
- Only `Box`, `Text`, `Button` and `Input` from `$.ui.resolve(e)` are used, with the props the
  file already uses (`flexDirection`, `gap`, `marginBottom`, `borderStyle`, `paddingX`,
  `flexGrow`, `color`, `dimColor`, `bold`, `wrap`; `Input`: `key`, `label`, `placeholder`,
  `value`, `submitLabel`, `onInput`, `onSubmit`). No new component, no new prop.
- `refresh()` fetches the thread list next to the count and the contacts; the open thread is
  refetched by `act()` after every action, so a press shows its result without a model turn.
- The classic hook path is unchanged: `hooks/hooks.json`, `hooks/owl-count.sh`,
  `/owlpost:inbox` and the `FileChanged` wake keep working exactly as today with mods off.

Out of scope, noticed while reading (a separate task, not fixed here): the Ask view's `send()`
builds `owl ask --peer <fp> --file <path> <question>`, but §9 defines `--file` as the git-blame
peer proposal and the path as a positional argument, so the Ask view sends the wrong argv today.

### 5. Plugin text and docs

- `plugins/claude-code/commands/thread.md` (new, `allowed-tools: Bash(owl thread:*)`): run
  `owl thread` for the list, `owl thread <peer>` for one conversation, paste the output
  verbatim. Without it three parity tests fail (`tests/plugin.rs::every_subcommand_has_a_command`,
  `::commands_have_descriptions`, `::readme_and_skill_list_every_command`), so the README command
  table gains its row and `skills/owlpost/SKILL.md` names `/owlpost:thread` in the same PR.
- `commands/inbox.md` and the skill keep their flow; one sentence each points at
  `/owlpost:thread` for the history of one person. The consent rules of OWL-036 are untouched.
- `plugins/claude-code/README.md` "Claude Code mods": the pane's inbox is described as a thread
  list that opens one conversation, with the actions on the open request only.
- `docs/technical-design.md` §8 (the `meta.events` log, its kinds, the write points, the derived
  log for legacy records), §9 (the `owl thread` row, `context_id` in the two `--json` listings);
  `docs/guide.md` a new section 3.11 "The whole conversation with one person".

### Open questions for the operator
1. `owl thread` shows every peer that ever wrote, including one whose contact has since been removed (the name falls back to the fingerprint). Should a removed contact's thread stay listed, or be hidden behind a flag?
2. The timeline shows the full text of every message. On a long thread the human format can run to hundreds of lines; is a `--last <n>` cut wanted now, or is `--since` enough?
