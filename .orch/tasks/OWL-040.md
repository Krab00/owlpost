## Description

Decision (2026-09-14): the third and last kind of request in a thread. A peer sends the **name
of a tool** from a registry I configured and an **input object**; the request is held for my
consent like every content request; when I run `owl draft <id>` the tool runs on my machine; the
result is redacted, stored on the record and, on my explicit `owl send`, goes back to the peer.
Both sides then see in the thread what ran, with what input, and what came out.

The rules of OWL-039 hold unchanged and are the reason this task is safe at all:

1. **Manual consent, per request, every time** — policy `auto` never applies to a tool-call
   request; `never` still short-circuits to `403`.
2. **The registry is the allowlist** — only a tool the owner configured by name can be named,
   and the input is never interpolated into its argv. An unknown tool is a `4xx` at the API and
   never reaches consent.
3. **Nothing runs at arrival, and nothing runs on `allow`.** The daemon never spawns a child for
   a tool-call request. The only process that ever executes the tool is the CLI, inside
   `owl draft <id>`, which a human types after allowing the request.

### 1. Envelope (§6) — two more `Kind` variants

For the reason given in OWL-039 §1 (`Body` is `#[serde(untagged)]`, so a body discriminator
fails silently while a `Kind` variant fails at compile time), the tag is again the kind:

```rust
#[serde(rename = "tool-call")]  ToolCall,
#[serde(rename = "tool-reply")] ToolReply,
```

```json
{ "tool": "test", "input": { "package": "auth", "filter": "session" }, "project": "github.com/company/monorepo" }
{ "output": "…", "exit_code": 0, "duration_ms": 4120, "truncated": false, "redactions": 1, "harness": "human" }
```

```rust
ToolCall {
    tool: String,
    input: serde_json::Map<String, Value>,
    #[serde(default, skip_serializing_if = "Option::is_none")] project: Option<String>,
},
ToolReply {
    output: String,
    exit_code: i32,
    duration_ms: u64,
    truncated: bool,
    redactions: u32,
    harness: String,      // always "human"
},
```

- `input` is a JSON **object** (never a bare string or array), capped at the tool's
  `max_input_bytes` measured on its compact serialisation.
- `MAX_OUTPUT_BYTES: usize = 262_144`, the same cap and the same character-boundary cut as
  OWL-039's content, with `truncated: true` when it bites. The output carries no `sha256`: it is
  the record of one run, not a file the asker can re-derive.
- `exit_code` is the child's code, or `-1` when the tool was killed by a signal or by the
  timeout (`duration_ms` then equals the timeout).
- `context_id` threads exactly as for a question and a content request; `envelope::a2a_state`
  again gains **no row**.

### 2. Config (§3) — the tool registry

```json
"responder": {
  "tools": {
    "test":  { "argv": ["cargo", "test", "--workspace"], "cwd": "github.com/company/monorepo", "timeout_ms": 600000, "max_input_bytes": 4096 },
    "build": { "argv": ["cargo", "build"], "cwd": null, "timeout_ms": 300000, "max_input_bytes": 1024 }
  }
}
```

`BTreeMap<String, Tool>`, empty by default (`owl init` writes `{}`), so the feature is off until
the owner adds a tool by hand. `Tool { argv: Vec<String>, cwd: Option<String>, timeout_ms: u64,
max_input_bytes: usize }`. Rules, each of them a refusal the tests pin:

- `argv` must be non-empty; `argv[0]` is resolved on `PATH` like a harness command.
- **The input never touches argv.** It is written to the child's stdin as the compact JSON of the
  `input` object followed by one `\n`, and stdin is closed. No `{input}` placeholder exists, and
  a config whose `argv` contains the literal `{input}` is refused at load
  (`config: tools.<name>.argv must not interpolate the input`). The tool reads its arguments from
  stdin or it is not usable here.
- `cwd` names a key of `config.projects` (the checkout the tool runs in) or is `null` (then
  `$OWLPOST_HOME`). A `cwd` naming an unknown project is refused at load.
- Environment: `OWLPOST_TOOL=1`, `OWLPOST_TOOL_NAME=<name>`, `OWLPOST_PEER=<fingerprint>`, PATH
  inherited; nothing else is added and nothing from the request reaches the environment.

### 3. Server (§7) — same route, same consent, one more validation arm

`validate_request` (OWL-039 §3) gains `tool-call`; `type` may now be `question`, `content` or
`tool-call` (`400 type must be question, content or tool-call`).

| Check | Response |
|---|---|
| `body.tool` missing, empty, or not a key of `responder.tools` | `400 unknown tool` |
| `body.input` missing or not a JSON object | `400 body.input must be an object` |
| compact `body.input` longer than the tool's `max_input_bytes` | `400 input is <n> bytes, max <m>` |
| `body.project` present and not a key of `config.projects` | `400 unknown project` |
| `responder.tools` empty | `400 unknown tool` (no registry, nothing to name) |

`unknown tool` deliberately does not distinguish "no such tool" from "no registry": a peer must
not be able to enumerate the owner's tools by their error messages.

Then, as in OWL-039: `never`/responder disabled → `403`; otherwise the record is spooled
**`consent`** for every policy (`record_state_for(Kind::ToolCall, _) == ("consent", false)`); no
cache read, no cache write; `202 … TASK_STATE_SUBMITTED`. `auto::not_a_candidate`'s kind guard
covers `Kind::ToolCall` with `record <id> is a tool-call request — consent only`.

Nothing in `src/server.rs`, `src/daemon.rs`, `src/auto.rs` or `src/pull.rs` ever constructs a
`std::process::Command` for a tool. The spawn lives in `src/tools.rs` (new), called only from
`src/cli/draft.rs`.

### 4. CLI (§9)

- **Asker** — `owl call <peer> <tool> --input <file|-> [--project <id>] [--reply-to <id>]`.
  The input file must parse as a JSON object (`exit 1 input must be a JSON object`), is sent
  verbatim, and the `asks/` record gets the event `tool-requested`. Prints
  `accepted <id> — waiting for the owner's consent`; `--json` adds `"state"`. No `--wait`, for
  the reason given in OWL-039.
- **Responder** — `owl inbox` lists the record with `type: "tool-call"` and `summary` =
  `<tool> <compact input, cut to 60 chars>`; `owl show <id>` prints the tool name, the resolved
  `argv`, the `cwd` and the input pretty-printed, so the human sees exactly what would run before
  allowing anything. `owl allow` / `owl deny` behave as always.
  - `owl draft <id>` on a tool-call record is the **only** thing that runs the tool. It refuses a
    record still in `consent` with the existing message, spawns `argv` in `cwd` with the input on
    stdin, bounds the run by `timeout_ms` (kill on expiry, `exit_code: -1`), captures stdout and
    stderr into one stream (stdout first, then stderr under a line `--- stderr ---` when stderr
    is non-empty), runs `runner::redact`, cuts at `MAX_OUTPUT_BYTES` and stores the result as the
    draft together with `exit_code`, `duration_ms`, `truncated`, `redactions` and
    `harness: "human"`. It prints
    `ran test in 4.1s — exit 0, 3120 bytes, 1 redaction` (`truncated` appended when cut) and then
    the output. A non-zero exit is **not** a CLI failure: the draft is stored and `owl draft`
    exits 0, because a failing build is a legitimate answer; only a tool that could not be
    started at all is exit 1 (`tool test: no such file or directory`). `--harness`, `--text`,
    `--agent` and `--prompt` are refused as in OWL-039.
  - `owl send <id>` signs a `tool-reply` and queues it; `owl reject <id>` discards it. As in
    OWL-039, `send` omits `envelope::question_hash` and the outbox record's `meta.hash` for this
    kind (`answer::question_body` errors on a `ToolCall` body), not only the cache write.
  - **The result stays on my side.** `answer::finish` for a tool-call record keeps the draft on
    the `done/` record (it is not cleared on send), so `owl thread` and `owl show` still show
    what ran, with what input and what came out, after the reply has gone.
- **Asker again** — the pulled reply lands in `inbox/` as a `tool-reply` record; `owl show` prints
  `exit <code> · <duration> · <n> bytes` and the output in a plain ```` ```text ```` block, with
  OWL-039's 200-line display cap.
- **Thread** — the event kinds `tool-requested` (out), `tool-run` (`by: "human"`,
  `detail: {"tool": "test", "exit_code": 0, "duration_ms": 4120}`), `tool-sent` and
  `tool-received`, all plain strings in `meta.events`.
